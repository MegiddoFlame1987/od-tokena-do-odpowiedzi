From Task to Agent

A model answers. An agent acts. An agent is the same model, run in a loop, with tools and a stopping condition. A tool is a function that a program runs when the model asks for it. Then comes the scratchpad, which is what the agent writes down so that it does not forget. And permissions: what it is allowed to do without asking a person. This page shows each of those parts on its own. At the end: where this arrangement breaks, and how to spot a task worth handing to an agent.

Part I

Loop

One difference explains all the rest. A model called once writes text. A model called in a loop carries out a task.

1 / 15

Model, assistant, agent

Three words that blur into one in conversations about AI. They differ in how much is left for you to do. The same task, three arrangements.

    Verified: underneath, the same model is working in all three cases. The difference comes from the casing around it: whether it was given tools, and whether it is run many times in a row. Simplified: splitting this into three categories is a convention, products shade into one another.
    2 / 15

    The agent loop

    The heart of the matter. The model gets a goal, picks one action, sees the result and decides what next. Then again. Click through it step by step.

    Scratchpad:
    Verified: every agent system in use today comes down to this loop, whatever the vendor. The model does not perform the action itself, it writes a request that a program next to it carries out. Simplified: the plan and the assessment often happen inside one call to the model, not as separate stages.
    3 / 15

    What ends the loop

    A loop with no brake spins until the money runs out. That is why every agent has several stopping conditions at once.

    BrakeWhat it meansWhat happens when it is missing
    Success conditionIt can be checked that the goal has been reachedThe agent circles the task, adding one correction after another
    Step budgetThe maximum number of turns of the loopIt sticks on one error and repeats it over and over
    Token or time budgetA cost limit for one task. A token is a piece of text that the model cuts a sentence into. Cost is counted from tokensThe bill grows with no result
    Question to a personThe agent stops and asks instead of guessingIt guesses and carries on from a wrong assumption
    Verified: limits on steps and on budget are standard in every serious piece of software for building agents. In practice: the success condition is the hard part. If you cannot write it in one sentence, the task is not ready for an agent yet.
    Part II

    Anatomy

    Five parts that make up every agent. Change one and the behaviour of the whole thing changes.

    4 / 15

    Five parts

    There is nothing else inside. If an agent behaves differently from what you want, the problem sits in one of these five things.

    PartRoleTypical symptom when it is set up badly
    ModelDecides what to do in the next stepGood tools, poor decisions. The model is too weak for the task
    InstructionThe goal, the rules, what is not allowedThe agent does something correct, but not what was meant
    ToolsThe only way the agent touches the worldThe agent describes what it would do instead of doing it
    ScratchpadWhat the agent knows after the tenth stepIt forgets what was settled at the start and repeats work already done
    Loop and limitsHow many times and for how longIt finishes too early, or it does not finish at all
    Verified: this split matches what you actually set up in the API and in the software for building agents. An API is the way a program talks to the model without a chat window. Simplified: in finished products several of these parts are fixed in place and invisible to the user.
    5 / 15

    Tool

    The moment the model stops only writing. Every tool has a name and a description. The model writes a request, the program carries it out. The result comes back as text into the context window, which is everything the model sees at a given moment.

    Verified: the model never runs code or a query itself. It writes a request in a fixed format. A program next to it carries that out, and the result comes back into the window. Simplified: every model vendor has a slightly different request format. What is shown here is a shorthand.
    6 / 15

    The scratchpad, the memory of an agent

    After thirty steps an agent does not remember the first one, unless somebody wrote it down. Agent memory is not magic. It is a decision about what goes into the window.

    KindWhere it livesWhat survivesCost
    Step historyContext windowTo the end of the task, as long as it fits in the windowGrows with every step
    SummaryThe window, once the history has been shortenedSurvives, but loses the detailLow, at the cost of accuracy
    Working fileDisk or a repository, that is a project folder with a history of changesSurvives the end of the taskIt has to be read and written deliberately
    Long-term memoryA separate store, appended to the windowSurvives between tasksNeeds rules about what to save
    Verified: the weights of the model do not change while an agent works. Everything the agent "remembers" is text put into the window at every step. The mechanism is the same as in an ordinary chat, described in the section on memory. In practice: long tasks break on the summary most often, not on a lack of intelligence.
    7 / 15

    Permissions

    The most important design decision, and the only one that is genuinely yours. It is not about what the agent can do, it is about what it is allowed to do without asking.

    Kind of actionReversibleSensible default setting
    Reading: files, pages, a databaseYesNo need to ask
    Working write: a draft, a copy, a separate version of a fileYesNo need to ask
    Overwriting existing dataPartlyAsk, or keep a backup
    Sending a message to the outsideNoAlways ask
    Payment, order, contractNoAlways a person, not an agent
    Deletion, change of permissionsNoAlways a person, not an agent
    Verified: splitting actions by whether they can be undone is standard practice in agent design. The main model vendors have it written straight into their consent settings. Reasoned: the specific thresholds in this table are a proposal, not an industry standard.

    Kinds

    How agents differ from one another. Two axes are enough: how much the model decides, and how many agents work at once.

    8 / 15

    Five levels of autonomy

    Move the slider. One thing changes: how many decisions stay with the model, and how many stay with you.

    Human decisionsModel decisions
    Verified: more autonomy always means less oversight in exchange for faster work. The fewer the stopping points, the faster the task runs and the later an error surfaces. Simplified: a five-step scale is a convention for teaching, not a standard. Different authors split it differently.
    9 / 15

    Workflow versus agent

    The most common mistake in a rollout: building an agent where a workflow is enough, that is a fixed script of steps. There is one difference. Who sets the order of the steps.

    WorkflowAgent
    Order of stepsWritten down in advance by a personChosen by the model as it goes
    The model insideCarries out single steps, summarising for exampleDecides which step comes next
    RepeatabilityThe same result for the same inputThe result can differ between runs
    Cost of a runPredictableVariable, depends on the number of steps
    When to choose itThe process is known, repeatable, stableEvery case looks different, the steps cannot be listed in advance
    Verified: the workflow versus agent distinction is the basic split in the technical documentation of model vendors. In practice: if you can draw the process as a flow chart with no branches that depend on content, build a workflow. Cheaper, faster, predictable.
    10 / 15

    One agent versus a team

    When a task is broad, several agents are run at once instead of one long chain. An orchestrator is an agent that splits the task and merges the results. Subagents each get a piece. Each has its own window and comes back with a conclusion, not with raw material.

    ArrangementStrengthWeakness
    One agentFull context in one place, one consistent decisionThe window fills up, the run takes a long time
    Orchestrator and subagentsWork in parallel, every subagent has a clean windowA subagent does not see the whole, the conclusions have to be merged
    Verified: subagents with separate windows are a working arrangement when reviewing many sources and large numbers of files. Reasoned: working in parallel pays off only where the subtasks are genuinely independent. When step two depends on step one, a team of agents gives nothing.
    Part IV

    What it can do

    Without enthusiasm and without dismissal. Agents are strong on one specific shape of task and weak on everything that departs from that shape.

    11 / 15

    The shape of task that works

    It is not about the field, it is about the structure. The same question asked differently is sometimes right for an agent and sometimes not.

    Feature of the taskGoodBad
    Checking the resultIt can be checked automatically: a test passes, a file opens, the numbers add upJudging it is a matter of taste, or it needs an expert
    Access to dataEverything needed is available through toolsThe key piece of information is in somebody's head
    Consequence of an errorReversible, visible straight awayIrreversible, or it surfaces a month later
    Number of stepsFrom a few to a few dozenHundreds of steps with no checkpoint
    RepeatabilityThe task comes back, so it is worth setting up well onceOne-off, faster to do by hand
    Verified: whether the result can be checked automatically is the best predictor of whether an agent will cope with a task. Hence the advantage agents have in programming. Tests say straight away whether the code works. Reasoned: the other four rows follow from the mechanics of the loop, they are not a measurement.
    12 / 15

    Five uses and what is left to the person

    A sensible division of work looks the same in each of these cases. The agent searches and writes a draft. The person decides and answers for the result.

    UseWhat the agent does wellWhat is left to the person
    CodeReads the repository, writes a change, runs tests, fixes it after an errorThe decision whether to design it that way. Review of the change
    Source review (research)Reads dozens of sources at once, sets contradictions side by sideChoosing the question and judging how reliable the sources are
    Documents and dataPulls data out of hundreds of files, makes the format uniformThe rule for what counts as correct. Checking a sample
    Operations and reportsCollects data from several systems, writes a draft reportInterpretation and conclusions. Talking to people
    Handling ticketsSorts tickets, answers the typical ones, gathers the background of a case for a personThe unusual cases and everything that touches money
    Verified: these five areas are where agents are rolled out most widely today. Not verified: the size of the savings. Published numbers come mainly from vendors and nobody has checked them independently. Before a rollout, measure your own baseline: how long the task takes today.
    Part V

    Where it breaks

    Two mechanisms account for most failed rollouts. Both follow directly from the build of the loop, so they can be predicted before anything goes wrong.

    13 / 15

    Error builds up in the loop

    A step that works in 95 cases out of 100 sounds good. Twenty such steps in a row does not. Move the sliders.

    Two levers: raise the success rate of a single step (a better model, better tools) or shorten the chain (fewer steps, a checkpoint halfway). Check on the sliders which one gives more at your numbers.
    Verified: the arithmetic is simple and true for independent steps: the success rate raised to the power of the number of steps. Simplified: in a real agent the steps are not independent. An agent often notices its own error and backs up, which raises the result. It can also carry one bad assumption through the whole task, which lowers it. This curve shows the mechanism, not a forecast.
    14 / 15

    Data is not instructions

    An agent reads a page, a file or a message. For the model, everything that lands in the window is the same kind of text. If somebody writes an instruction inside a document, the model may treat it as yours. That is a prompt injection.

      SafeguardWhat it gives
      A clear marking in the window of what is an instruction and what is materialThe model sees the boundary. The risk drops, but it does not disappear
      Tools with narrow permissionsEven a hijacked agent has nothing to do damage with
      Consent from a person before an action that cannot be undoneThe single most effective protection
      Split roles: one agent reads, another actsContent from outside never reaches the tools that change something
      Verified: prompt injection is a described and well known kind of security hole. The model on its own cannot fully defend against it. That is why control moved to permissions and consent. In practice: there is one rule to remember. Content the user did not write is material, never an instruction.
